# 批量导入与批量转换 — 设计方案

Status: ready-for-agent
日期：2026-09-23（输出规则修订：2026-09-23 第二轮）
Feature slug: `batch-import`
范围：本 spec 只覆盖「拖入 .blf / 文件夹 → 候选清单勾选 → 共用一套配置 → 批量转换」；
压缩包（zip/7z/rar）拖入为下一阶段，见 Out of Scope。**但输出位置规则已把压缩包一并定义**
（见 Implementation Decisions），下一阶段直接复用。

---

## Problem Statement

一次测试跑完，数据通常是一批而不是一个：一个文件夹里躺着 N 个 BLF，或者上游发来一个压缩包。
但目前「输入 BLF」一次只能吃一个文件，用户被迫做大量重复劳动：

- 拖入文件夹或压缩包**不被识别**，只能先手动解压、再逐层点进目录，找到一个 .blf 选一个；
- 转换一批文件要重复 N 遍「选择文件 → 等扫描 → 配平台 → 配项目 → 逐个通道确认 DBC → 点开始转换」；
- 每换一个文件，平台/项目/DBC 绑定都要重新配一遍，而同一批数据这些配置**本来就是同一套**；
- 一批文件转完之后没有一个整体结论，用户要自己记「哪几个转过了、哪几个失败了」。

结果就是：批量数据用单文件工具处理，时间大量花在重复点击上，且容易漏转、错配。

## Solution

把「输入 BLF」从单文件入口升级为批量入口，同时**不牺牲单文件流程**：

1. **拖入可以是三种东西**：一个 .blf（原行为不变）、一个文件夹（递归找出里面所有 .blf）、
   （下一阶段）一个 zip/7z/rar 压缩包（解压后同样递归）。
2. **候选清单**：来源解析完成后弹出勾选列表，支持逐个勾选与全选，并显示已选计数。
   候选只有 1 个时直接进入，不弹列表。
3. **共用一套配置的显式提醒**：实际参与批量的文件超过 1 个时，弹窗告知用户这些文件将共用
   同一套「平台 + 项目 + CAN-DBC 绑定」，用户点确认后才进入配置环节；只勾选 1 个文件时
   不弹窗，直接走今天的单文件流程。
4. **一次配置，整批生效**：平台、项目、CAN-DBC 绑定对整个批次只配一次；绑定表的通道集合
   由这批文件的通道**并集**决定。
5. **一次启动，逐个转换**：点「开始转换」后按顺序转换每个文件，进度显示当前是第几个（i/N）。
6. **产物落在与源同级的镜像树里**（直接拖入的 .blf 除外）：

   | 拖入的东西 | 产物落在哪 |
   |---|---|
   | 单个/多个 .blf | 就在该 .blf 自己旁边（今天的逻辑不变） |
   | 一个文件夹 | 与文件夹**同级**的镜像树 `<文件夹名>_t/`；树内目录沿用原名，MDF 文件名追加 `_t` |
   | 一个压缩包（下一阶段） | 与压缩包**同级**的镜像树 `<压缩包名>_t/`；同样规则 |

   镜像树只复刻「通向至少一个 .blf」的目录，空目录与无关文件不复制。
7. **一个整体结论**：全部转完后弹出结果——全部成功时告知「N 个 blf 文件全部转换完成」；
   有失败时告知「N 个 blf 文件转换成功 X 个，失败 Y 个」并列出失败文件名。

用户的操作从「N 次单文件流程」收敛为「拖一次 → 勾一次 → 配一次 → 点一次」，
且原始数据与转换产物自然分成两棵并排的树，便于整体交付。

## User Stories

### 来源与候选清单

1. 作为测试工程师，我想把一个装有 N 个 BLF 的文件夹直接拖进「输入 BLF」，以便不必逐个点进目录去选文件。
2. 作为测试工程师，我想让工具递归找出文件夹里（含各级子目录）的所有 .blf，以便数据放在多层目录里也能一次拿全。
3. 作为测试工程师，我想直接拖入单个 .blf 文件，以便单文件场景完全保持今天的手感。
4. 作为测试工程师，我想一次拖入多个条目（多个文件夹、多个文件混合），以便把分散的数据一次性汇总成候选清单。
5. 作为测试工程师，我想让扩展名识别大小写不敏感（.blf / .BLF / .Blf），以便从资源管理器拖出的文件不会因为大小写被漏掉。
6. 作为测试工程师，我想在候选清单里看到每个文件的**相对路径与大小**，以便区分同名但不同目录的文件、并判断哪个是大文件。
7. 作为测试工程师，我想让候选清单的文件排序**确定**（同样的拖入每次顺序一致），以便我可以按肌肉记忆勾选。
8. 作为测试工程师，我想在候选清单里提供**全选**与**全不选**，以便默认全要、或快速清空重勾。
9. 作为测试工程师，我想逐个勾选，以便只转我关心的那几个。
10. 作为测试工程师，我想在候选清单上看到**已选 N / 共 M** 的计数，以便确认自己没有漏勾。
11. 作为测试工程师，我想在同一个来源里出现重复文件（软链接/重复拖入）时自动去重，以便不会转出两份一样的产物。
12. 作为测试工程师，我想在文件夹里**一个 .blf 都没有**时得到明确提示（而不是静默什么都没发生），以便知道我拖错了地方。
13. 作为测试工程师，我想在搜集过程中遇到无权限、被占用的子目录时**跳过并记日志**而不是整个失败，以便一个坏目录不会毁掉整次导入。
14. 作为测试工程师，我想在遍历大目录树时看到进度并可**取消**，以便拖错了一个巨大目录时能立刻停下。
15. 作为测试工程师，我想在搜集/扫描进行中拖入被拒绝（与今天「浏览…」按钮禁用一致），以便不会出现「接受了却没反应」的困惑。
16. 作为测试工程师，我想勾选完点取消能回到原状，以便不必重开工具。
17. 作为测试工程师，我想在只找到一个 .blf 时**不弹勾选列表**直接进入，以便「拖一个文件夹里面只有一个文件」不被多余的一步打断。

### 共用一套配置

18. 作为测试工程师，我想在**实际参与批量超过 1 个文件**时被明确告知「这些文件将共用一套配置」，以便我事先知道后续的平台/项目/DBC 选择会作用于全部文件。
19. 作为测试工程师，我想在只勾选 1 个文件时**不看到**这个提示，以便单文件操作不被无意义地打断。
20. 作为测试工程师，我想在提示里看到**这一批会共用哪几项配置**（平台、项目、CAN-DBC 匹配）以及「切换会同时作用于全部文件」，以便我理解后果。
21. 作为测试工程师，我想在提示里被告知「某个文件中不存在的通道不会被导出，该文件的输出会相应少几组信号」，以便事后看到某份 MDF 组数少时不会以为是工具出错。
22. 作为测试工程师，我想在提示上点「返回勾选」时**不改变任何现有配置**，以便反悔后代价为零。
23. 作为测试工程师，我想让平台（CCU 版本）的选择对整个批次生效，以便一批同平台的数据只配一次。
24. 作为测试工程师，我想让项目的选择对整个批次生效，以便一批同项目的数据只配一次。
25. 作为测试工程师，我想让 CAN-DBC 绑定表由这批文件通道的**并集**构成，以便某通道只在部分文件里出现时它仍然出现在表里可配。
26. 作为测试工程师，我想让「某些文件没有该通道」成为**正常情况而不是错误**——缺它的文件不导出该组，其余文件照常导出。
27. 作为测试工程师，我想让「所有选中文件都没有该通道」的映射通道显示为**无数据**，以便沿用今天的三态语义。
28. 作为测试工程师，我想在批量转换进行中无法修改平台/项目/绑定，以便不会出现「转了一半换了配置」的批次内不一致。
29. 作为测试工程师，我想让候选清单、平台、项目、绑定这套配置在整批转换期间保持稳定，以便输出结果可复现。

### 输出位置

30. 作为测试工程师，我想在直接拖入 .blf 时让产物就落在它自己旁边（`<主名>_t.mdf`），以便单文件操作与今天完全一致。
31. 作为测试工程师，我想在拖入文件夹时让产物落在**与文件夹同级的镜像树** `<文件夹名>_t/` 里，以便原始数据与转换产物并排存放、互不干扰。
32. 作为测试工程师，我想在拖入压缩包（下一阶段）时让产物落在**与压缩包同级的镜像树** `<压缩包名>_t/` 里，以便不必先解压再手工整理产物位置。
33. 作为测试工程师，我想让镜像树里的目录**沿用原目录名**（只有树根带 `_t`）、只有 MDF 文件名追加 `_t`，以便从产物路径就能反推它在源里的位置。
34. 作为测试工程师，我想让镜像树**只复刻通向 .blf 的目录**，空目录与无关文件（说明、日志等）不复制，以便产物树干净。
35. 作为测试工程师，我想让源文件夹里直接躺着的 .blf 也照此落位（`<源名>_t/<主名>_t.mdf`），以便规则没有例外。
36. 作为测试工程师，我想让产物树**落在源的同级**而不是源内部，以便不会把产物混进原始数据里。
37. 作为测试工程师，我想在只选 1 个文件时仍能**手动改输出路径**（输出框可编辑，且手改值优先），以便单文件场景保留今天的自由度。
38. 作为测试工程师，我想在批量（> 1）时输出框**只读**并禁用「浏览…」，以便不会产生「改了却没生效」的误解。

### 批量转换

39. 作为测试工程师，我想在点「开始转换」后看到**当前是第几个文件（i/N）+ 该文件内部的阶段**，以便知道还要等多久。
40. 作为测试工程师，我想在批量开始前**一次性**被检查所有输出路径是否已存在，并一次决定「覆盖全部 / 跳过已存在 / 取消」，以便不必面对 N 个覆盖确认弹窗。
41. 作为测试工程师，我想在某个文件转换失败时工具**继续转换剩余文件**，以便第 3 个文件坏掉不会让后面 9 个白等。
42. 作为测试工程师，我想在转换失败的文件上**遵守无残留契约**（不留半成品，该路径上一次成功的产物保留），以便失败不会污染已有产物。
43. 作为测试工程师，我想在取消批量时**停止队列、清理当前在转文件、保留已完成文件的产物**，以便取消不等于丢弃前面的劳动成果。
44. 作为测试工程师，我想在整批结束后看到一个**结果弹窗**：全部成功时显示「N 个 blf 文件全部转换完成」，有失败时显示「N 个 blf 文件转换成功 X 个，失败 Y 个」并列出失败文件名，以便一眼知道这批活干完没有。
45. 作为测试工程师，我想在日志里看到每个文件的耗时与结果（成功/失败原因），以便事后对账与排查。
46. 作为测试工程师，我想在批量转换进行中禁用会改变批次的控件（与今天的忙碌态一致），以便不会转一半改输入。
47. 作为测试工程师，我想在批量转换进行中关闭窗口时被询问确认，以便不会误关丢失进度。
48. 作为测试工程师，我想看到「输入 BLF」行显示这一批的**来源与文件数**（而不是只显示一个路径），以便确认当前批次是不是我要的那批。

### 单文件回归

49. 作为测试工程师，我想在只选 1 个文件时**行为与今天完全一致**（输出路径可手改、完成提示、日志文案），以便日常单文件操作零学习成本、零回归风险。
50. 作为测试工程师，我想让今天所有已有的行为（扫描进度、取消扫描、绑定状态三态、转换取消、摘要、日志）在批量下语义一致，以便不必为批量重新学一套概念。

## Implementation Decisions

**新增两个 core 模块（均无 Qt、可脱离界面直接测）**

- **来源解析模块**：输入用户拖入的路径集合，输出候选清单。每个候选携带三项决定好的信息：
  **BLF 路径、输出路径、相对显示名**（外加大小）。职责：识别条目类型（单文件/文件夹；
  下一阶段扩展压缩包）、递归搜集、扩展名大小写不敏感匹配、去重、确定性排序、无权限目录跳过、
  进度与取消上报。**输出路径在解析期一次算定**，下游不再重算。不感知平台/项目/DBC，也不感知转换。
- **批量编排模块**：输入待转清单（BLF、输出路径）+ 一套绑定 + 进度回调 + 取消回调，逐个调用既有
  单文件转换，输出逐文件的成功结果或失败原因。职责：批内顺序、进度映射（整体进度 = (i + 文件内进度)/N）、
  失败继续、取消收口。**这是「批量」这一概念的唯一定义处**——界面层不得自己写循环。

**输出路径规则（本次修订的核心）**

| 来源 | 输出路径 | 例 |
|---|---|---|
| 直接拖入的 .blf | 该 .blf 同目录，主名 + `_t.mdf` | `E:\data\run005.blf` → `E:\data\run005_t.mdf` |
| 拖入的文件夹 | **同级**镜像树 `<文件夹名>_t/` + 相对路径，文件名 + `_t.mdf` | `E:\data\AHT\20260917\run001.blf` → `E:\data\AHT_t\20260917\run001_t.mdf` |
| 拖入的压缩包（下一阶段） | **同级**镜像树 `<压缩包名>_t/` + 压缩包内相对路径 | `D:\drops\A02.zip` 内 `run1\r1.blf` → `D:\drops\A02_t\run1\r1_t.mdf` |

三条约束（已确认）：

- **只有树根带 `_t`**，树内目录沿用原名；只有 MDF 文件名追加 `_t`。
- 镜像树落在**源的同级**，绝不落在源内部（不污染原始数据）。
- **只复刻通向至少一个 .blf 的目录**；空目录与无关文件（说明、日志等）不复制。
  注意：不含 .blf 但位于某 .blf 路径上的中间目录**要**创建，否则路径不成立。

一次拖入混合来源（既有文件夹又有散 .blf）时，两类候选各按各的规则落位，互不影响。

**界面层改动（保持薄）**

- 拖拽入口：从「取第一个 .blf」改为「把拖入的路径集合交给来源解析模块」，命中 0 个可导入项时整行拒绝（沿用今天的拒绝语义）。
- 窗口状态：从单个 BLF 路径改为**批次文件列表**；列表长度为 1 时所有既有行为（输出可手改、完成提示、日志文案）逐字保持今天的样子。
- 新增**勾选对话框**：列表 + 复选框 + 全选/全不选 + 已选计数 + 确定/取消；样式走既有主题令牌，与现有对话框同一视觉体系。**候选只有 1 个时不弹**。
- 新增**共用配置提示**：信息型弹窗，文案要点见 User Stories 18–21；触发条件 = 勾选确认后实际文件数 > 1。
- **完成弹窗分支**：批量为 1 时用今天的「转换完成。」；> 1 时用批量文案（全部成功 / 成功 X 失败 Y + 失败文件名列表）。
- **输出预检**：批量开始前检查所有输出路径，已存在的合成一次询问（覆盖全部 / 跳过已存在 / 取消）；单文件沿用今天的单次确认。
- 输出框：批量（> 1）时只读并禁用「浏览…」；单文件时保持今天唯一可手改输入框的地位，且**手改值优先于解析算出的输出路径**。
- 「输入 BLF」行在批量时显示来源与文件数（如「12 个文件 · 来自 AHT」），完整清单进 tooltip。

**批内串行，文件内并行**

批次内一次只转一个文件（顺序执行），每个文件内部仍走既有的并行解码路径。理由是单份 BLF 可达 GB 级、
转换本身已吃满 CPU 与内存，批内并发会让内存峰值成倍上升而没有相应收益。

**契约扩展（需同步写进领域词汇表 CONTEXT.md）**

- 新增**批次（batch）**词条：一次导入并经勾选确认的文件集合；一个批次共用一套平台/项目/绑定，
  转换顺序与输出规则由批次定义；批次的身份是「这一批文件 + 这一套配置」。
- 新增**镜像输出树**词条：文件夹/压缩包来源下产物落的树——与源同级、根名加 `_t`、树内目录沿用原名、
  文件名加 `_t`、只复刻通向 .blf 的目录。与「输出路径与 BLF 同目录」是两条并行规则，按来源类型分派。
- **取消信号**扩展：单文件取消 = 放弃本次转换（删除完整产物）。**批次取消 = 停止队列 + 当前在转文件
  按其自身契约清理 + 已完成文件的产物全部保留**。两者语义不同，必须分别记录，否则批量取消会退化成
  「丢掉前 6 个文件」。
- **无残留**扩展：批量下逐文件成立，且失败/取消**不得影响已完成文件的产物**。
- **绑定**词条的「无数据」定义扩展：批量下「无数据」= **所有选中文件中都不存在该通道**；
  只在部分文件中存在的通道属于正常三态（该文件不导出该组，其余文件照常）。
- **失败语义**：单文件失败不中断批次，失败原因计入日志与结束弹窗。
- 既有那句「输出文件路径始终与 BLF 文件路径一致」在文件夹/压缩包来源下**不再成立**，实施时
  必须连同代码注释一起改成上述分派规则。

## Testing Decisions

**什么是好测试**：只验证外部行为——「给什么输入得到什么产物/什么用户可见结果」，不穿透私有实现、
不锁定内部调用序列。现有测试体系已经按这个标准组织（core 直测 + 纯函数决策 + GUI 用窗口级行为断言）。

**接缝**（经确认：认可 core 两处接缝，并**加做 GUI 流程测试**）

1. **来源解析接缝**：直接调用来源解析模块，覆盖递归深度、大小写扩展名、去重、确定性排序、
   空结果、无权限目录跳过、多条目合并、取消；**以及输出路径映射**——三种来源各一组用例
   （散 .blf / 文件夹 / 混合），断言「镜像树同级、根带 `_t`、内层原名、文件名 `_t`、
   空目录不建」这五条约束逐条成立。无需 Qt。
2. **批量编排接缝**：用合成的 BLF 构造待转清单，覆盖顺序执行、进度映射、单文件失败继续、
   取消后「已完成保留 + 当前清理」、全部成功/部分失败的返回结构。无需 Qt。
3. **GUI 拖拽接缝（已存在，扩展）**：沿用现有做法——构造拖拽事件发给窗口，断言多来源 → 候选清单 →
   按勾选结果进入批量；对话框用 monkeypatch 短路。
4. **GUI 流程测试（新增）**：
   - 候选只有 1 个 → 不弹勾选列表，直接进入；
   - 勾选 1 个 → 不弹共用配置提示，走原单文件路径（输出框可手改、手改值优先）；
   - 勾选 12 个 → 弹提示，确认后才进入批量；
   - 提示上返回勾选 → 回到列表且现有配置未被改动；
   - 批量结束弹窗文案：全成功与部分失败两种分支（含失败文件名）。
5. **对拍硬门**：批量转 N 份的输出，与逐个单文件转同一批的输出**逐位一致**（沿用既有对拍工具与判定维度）。
   输出位置变化不影响这条判定——对拍比较的是**内容**，不是路径。

**先例**：core 侧沿用既有的转换器/读取器测试与合成 BLF 构造方式；纯决策函数沿用绑定决策的
「无 Qt 直测」写法；GUI 侧沿用既有窗口 fixture + 拖拽事件注入的写法；产物等价性沿用既有对拍链。

**回归硬门**：单文件（N=1）路径下的全部既有测试必须零改动通过。

## Out of Scope

- **压缩包拖入（zip / 7z / rar）**：下一阶段。技术选型与**解压位置建议**已实测/已给出，见 Further Notes。
- **批内并发转换**：不并行（理由见 Implementation Decisions）。
- **跨文件复用进程池**：阶段 2 的性能优化，需先有真实批量基线再决定（见 Further Notes 的实测开销）。
- **统一输出目录**（所有产物集中到一个用户指定目录）：本期规则是「散 .blf 就地 / 文件夹与压缩包进镜像树」，
  集中输出不在范围内。
- **完整复刻目录骨架**（连不含 .blf 的空目录也复制到镜像树）：本期只复刻通向 .blf 的目录。
- **每个文件各自一套绑定/项目**：本期一个批次一套配置；逐文件独立配置不在范围内。
- **「浏览…」的多选或选文件夹**：本期批量入口只做拖拽，浏览按钮保持单文件选择（与今天一致）。
- **加密压缩包、嵌套压缩包（压缩包里还有压缩包）、压缩包解压的路径穿越与体积上限收口**：随压缩包阶段一起做。
- **批次的持久化/断点续转**：转完即结束，不做队列存档。

## Further Notes

**压缩包后端选型（2026-09-23 本机实测，供下一阶段直接取用，勿重新调研）**

| 事项 | 实测结果 |
|---|---|
| Windows 自带 `System32\tar.exe` | bsdtar 3.5.2（+ `archiveint.dll` = libarchive 3.5.2），系统自带、零分发成本 |
| zip / rar4 / rar5 | ✅ 解压均通过；`../evil.txt` 被拒绝、盘符被剥离，**默认即防越界** |
| 7z | ❌ `LZMA codec is unsupported`——能识别格式但 Windows 的 libarchive 未编译 LZMA 解码器 |
| py7zr | ✅ 实测可列目录与解压，有密码检测与进度回调；依赖约 13MB（冻结打包需裁剪），PyPI 可达 |

结论：zip 与 rar 走系统自带 bsdtar，7z 走 py7zr，**不需要分发任何第三方二进制**。

**压缩包解压位置（下一阶段待定，本 spec 未定）**

输出树已定为「与压缩包同级」的 `<压缩包名>_t/`；解压树的位置仍是开放项。建议与之对称：
解压到与压缩包同级的 `<压缩包名>/`，两棵树并排（`A02\` 原始数据、`A02_t\` 产物），
既满足「解压树不在源内部」，也让产物树的落点规则保持一致。若压缩包所在位置不可写
（只读盘、网络盘），需要退回到可写位置的次级策略，这一条随压缩包阶段一并决策。

**已知性能开销（阶段 2 决策依据）**

单文件转换每次都会创建并预热一个进程池（既有实测 8 worker ≈ 1.7s 的启动与导入成本），
批量 12 个文件约 20s 纯开销。单份转换本身 12–45s，占比 4–14%。是否做跨文件共享池，
等阶段 1 落地后用真实批量基线决定。

**既有测试锚点（实施时注意）**

- 「输入 BLF」这个行标签被样式测试锚定，必须保持不变；
- 「输出路径是唯一可手改字段」被样式测试锚定，批量置只读后需要为批量分支增补断言（而不是改掉原断言）；
- 「忙碌态锁定控件」的断言列表被样式测试锚定，批量不新增常驻控件，该列表不需扩充。
